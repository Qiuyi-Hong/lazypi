# LazyPi architecture and Pi API findings (Phases 1–3)

Verified against [Pi package docs](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/packages.md), [CLI docs](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/cli.md), [extension docs](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md), [TUI docs](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/tui.md), and the installed Pi **0.87.1** `DefaultPackageManager`, `SettingsManager`, and package resolver. The [Pi gallery](https://pi.dev/packages) discovers npm packages using the `pi-package` keyword. Architectural reference: [kendex pi-extension-manager](https://github.com/vanillagreencom/kendex/tree/main/pi-extensions/pi-extension-manager), especially its inventory/actions/settings/versions/host/render/process separation; its `extensions: []` toggle only covers extensions, so LazyPi deliberately does not copy that behavior.

## Native mechanisms and corrections to the initial proposal

- `pi install <source> [-l]`, `pi remove <source> [-l]`, and `pi update <source>` operate on Pi package declarations; **bare `pi update` updates Pi itself**, not packages. Pi's `DefaultPackageManager` exports `installAndPersist`, `removeAndPersist`, and `update`, which LazyPi calls directly. `pi list`/`listConfiguredPackages()` includes both user and project declarations and their installation paths.
- Settings live in `<agent-dir>/settings.json` and `<cwd>/.pi/settings.json`. `<agent-dir>` defaults to `~/.pi/agent`, but can be overridden by `PI_CODING_AGENT_DIR`. Project declarations are usable only after Pi project trust; Pi's package manager resolves project identity ahead of user identity. Project `autoload: false` is a delta over the user entry, **not** a package-level disable flag.
- **Pi 0.87.1 does not expose a native package-level `enabled` boolean or `pi disable` command.** `pi config` controls individual resources. Pi's supported package source object accepts `extensions`, `skills`, `prompts`, and `themes`; `[]` for _each_ means that none of that type loads, while the package declaration and files remain. LazyPi's whole-package disable writes all four empty arrays to the Pi settings entry; enable restores the original string/default entry. This is a native Pi resource-filter mechanism used exclusively for package-level behavior. It does not stop npm install scripts or non-Pi package side effects.
- A package with only some filtered resources is **custom**, not disabled. LazyPi refuses to rewrite that state because restoring defaults would erase the user's resource-level choices. A user entry shadowed by a project entry is explicitly **shadowed**. Missing install paths are **missing**, not enabled. The two-state assumption does not cover Pi's richer states; displaying these truthfully is safer than inventing a separate flag.
- Pi packages contain any combination of extension, skill, prompt and theme resources; the `pi` manifest paths or conventional directories supply their types. npm `pi-package` keyword opts into gallery discovery. Pi-provided runtime imports use `peerDependencies` with `"*"` ranges, not ordinary dependencies. External curated packages remain separate Pi installations.

## Implementation boundaries

- `extensions/lazypi.ts`: command, confirmation, native reload, interactive-only guard.
- `src/packages.ts`: Pi settings/manifest inventory, scope/status, package-level filter toggle and operation text. Pi's `SettingsManager` handles locked settings writes and `DefaultPackageManager` owns install/remove/update. LazyPi never parses npm install directories or executes a shell command for these actions.
- `src/actions.ts`: thin native action boundary, injectable in tests; writes flushed and errors surfaced.
- `src/catalog.ts`: the predetermined Core baseline (`npm:pi-mcp-adapter`, `npm:pi-subagents`, `npm:pi-web-access`), each a separately installable Pi package.
- `src/ui.ts`: Pi `ctx.ui.custom` overlay, keyboard handling, selection/search/details, immediate local render without registry calls.
- `src/bootstrap.ts`: first-run reconciliation against Pi inventory, sequential native installation (user scope for new packages; original scope for configured-but-missing packages) after a confirmation plan, and an atomic `<agent-dir>/lazypi.json` completion marker. Existing user/project packages, disabled entries, pins, and filters remain untouched; a configured but physically missing Core package is repaired from its configured source. Failed installation stops the plan without removing successful installs. State writes preserve enabled Extra selections.
- `src/extra-catalog.ts`: curated Extras, one primary purpose category and independent resource types/tags per package; package-backed `id` and `name` are derived from their npm source (package-free workflows keep matching explicit fields). `src/extras.ts` reads legacy selection IDs and rewrites them only when selections are changed. [Download and manifest evidence](extras-curation.md). `src/extras.ts`: ordered purpose-category registry, deterministic browse/search filtering, dependency/conflict/source validation, `requiredBy` references and install/keep plans. Package-free dependency workflows have no invented source; package-backed Extras use `source` (and optional `packages` only for multi-package selections). Explicit selections only are saved in `<agent-dir>/lazypi.json` or trusted `<cwd>/.pi/lazypi.json`; Pi settings remain installation truth. Missing packages install in the requested scope (or repair their existing declaration); pre-existing packages and filters are adopted unchanged. Deselecting never auto-removes a package, since a Pi declaration cannot establish that LazyPi created it.

## Phase 3: Community and updates

- `src/community.ts` is a registry-only metadata adapter. npm's [registry search endpoint](https://github.com/npm/registry/blob/main/docs/REGISTRY-API.md) accepts `keywords:pi-package` and returns keyword-bearing packages; `/{name}/latest` returns the published manifest, including `pi` resource arrays. LazyPi validates npm names, filters search results by the actual keyword, extracts only declared resource types (absence means **unknown**, not none), and never treats registry rankings or metadata as a security score. Results matching Core/Extras identities are omitted from Community. Registry queries use public npm only; private registries configured in Pi's `npmCommand` are not searched.
- `<agent-dir>/lazypi-cache.json` stores bounded search pages and per-name latest manifests with timestamps and a one-hour TTL. Malformed cache data is ignored. Community and Updates load cached data synchronously, then refresh remotely after the popup has rendered; `r` bypasses TTL. No registry calls run for other tabs, and `PI_OFFLINE=1` uses cache only. Manifest details load on Enter. The first search page is limited to 30 results; pagination can be added if users need it.
- Updates compare installed unversioned npm packages with the registry's stable latest tag; other sources and npm version constraints are intentionally absent from automatic checks. Pi's `DefaultPackageManager.update(source)` remains the only updater: it handles scope and constrained sources according to native rules, and does not rewrite Pi's four disable filters. The remote cache is a hint, never installation truth. No shell/npm commands or duplicate package-state flags are introduced.

## Phase 4: local diagnosis and explicit reconciliation

- `src/polish.ts` derives sync repairs from Core and selected Extras against Pi inventory, retaining user/project scope, preserving custom filters and never removing unowned packages. `/lazypi sync` confirms the plan, checks for changes before execution and applies native actions sequentially; on failure successful steps stay applied and the user can retry. Explicit sync enables disabled requirements (first-run bootstrap still adopts them unchanged). `/lazypi health` inspects settings, installation paths, manifests and Extra selections read-only.
- `<agent-dir>/lazypi.json` stores only LazyPi preferences (`autoCheckUpdates` default off, `showCommunityPackages` default on) beside the existing bootstrap/Extra selection fields. The Settings tab changes preferences atomically; hiding Community affects tab navigation, not the shortcut or Pi package state. Enabled startup checking runs asynchronously after `session_start` and only notifies on newer eligible packages. Registry failures never block startup.
- Updates `U` fetches metadata, then confirms a native sequential update plan, deduplicated by npm identity across scopes; pinned, git and local sources are excluded. The user may retry after a partial failure; automatic rollback would risk removing or enabling pre-existing packages. Detail requests are ignored after popup disposal, and Extra package closures are cached per popup to keep repeated renders responsive.

Inventory and ordinary popup rendering make no registry calls; first-run setup uses Pi's native installer only after confirmation.
